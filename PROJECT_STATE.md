## Authoritative project principles

1. The Sanskrit source text is immutable.
2. Component 1 (Padaccheda) is the authoritative word inventory.
3. Every other component must reconcile to Component 1.
4. Source assertions, deterministic computational evidence, and engine decisions are separate evidence classes.
5. Ambiguous analyses remain ambiguous.
6. Missing Library evidence is a GAP or NOT_ASSERTED state, not an invitation to guess.
7. A Paninian/Laghusiddhāntakaumudī rule reference is not automatically a productive engine rule. Operational evidence must exist in the Library before generalization.
8. Exact deterministic joins are allowed; fuzzy matching is not.
9. The five benchmark ślokas remain fixed through Stage 30 and all subsequent improvement cycles.
10. Future stages modify the same `sanskrit_grammar_engine.py`; disconnected stage engines are no longer the deliverable model.
11. **(Stage 33)** Component 1 is authoritative from `sa_rAmAyaNa.txt`, not from any secondary Library artifact (e.g. the template test JSON). Secondary artifacts are used for cross-validation and for deriving other components, and a disagreement between a secondary artifact and Component 1 is reported as a diagnostic warning about that artifact, never as license to alter the authoritative Component 1 inventory.
12. **(Stage 36)** Reference rulebooks (systematic, sutra-cited grammar-rule compilations, as distinct from per-verse Library evidence) may be used ONLY to (a) attach a verified citation to a component value that already carries per-verse SOURCE_ASSERTION status — the citation must be looked up in the actual rulebook file at runtime and never fabricated — or (b) attach a non-binding candidate annotation to a still-pending/ambiguous item, without ever promoting that item's status. A rulebook is never used to classify an item that has zero per-verse evidence, and never used to synthesize a new Sandhi/Samāsa/other operation beyond what a Library file already asserts for that verse.

## Critical methodology finding (read before touching any of this again)

The user's initial review of a full-Sarga sandhi/samāsa report came back "almost 99% errors." The root cause was **not** that the underlying engines are broken — it was that the report generator had called `sandhi_splitter.split_word_recursive()` on **isolated GRETIL tokens one at a time**. That function looks for a sandhi boundary *inside a single already-complete word*, so run on a token that has no internal sandhi, it manufactures a fake internal cut (e.g. चारित्रेण → wrongly च+अरित्रेण). The fix was architectural, not a bug-for-bug patch: `combined_splitter.analyze_pada_line()` instead calls `samasa_splitter.restore_word_boundary()` **pairwise across adjacent tokens in the real verse line**, which is what actually detects genuine cross-word sandhi. Proved on the same 4 test cases with the identical underlying engine before/after: 0/4 correct via the wrong calling convention, 4/4 correct via the right one. **Any future sandhi/samāsa work on real verse text must go through `analyze_pada_line`'s pairwise pattern, never `split_word_recursive` on a lone token.**
